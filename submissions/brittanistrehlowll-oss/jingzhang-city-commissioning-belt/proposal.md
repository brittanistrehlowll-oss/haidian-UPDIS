# 京张·城市联调带
## JING-ZHANG CITY COMMISSIONING BELT
### AI时代的城市详规与真实场景创新｜A CIVIC AI OVERLAY FOR THE AI-NATIVE CITY

**一句话方案：** 不是给AI一块地，也不是把城市变成技术试验场，而是在一段真实北京城市空间里，建立让AI能力能够被规划表达、被场景验证、被公众理解、被人工接管并在必要时退出的城市规则。**城市设计与真实生活是主体，Civic AI Overlay 是规划创新，Compute–Power–Water 是专业支撑，C0–C6只是运行方法。**

> 本方案全部空间落位均为开放共创的概念建议。当前采用主办方仓库维护的 provisional_rough 临时边界，不代表官方红线；官方 polygon、控规、权属、文保和工程资料补齐后，所有面积、比例和地块级判断均须复核。 [source:BOUNDARY-SOURCE] [standard:PROJECT-OFFICIAL-ANNOUNCEMENT]

### 城市没有标准答案：让人类智慧与硅基智慧共同指向更美好的生活

人生没有标准答案，城市更没有标准答案。城市的意义不在于被某个规划师、机构或算法一次性“求解”，而在于让生活在其中的人能够持续感受、选择、创造和修正。过去，城市主要承载并放大人类的经验、制度与工程智慧；未来，来自人工智能系统的感知、计算、推理和协作能力，也会越来越深地参与城市。我们不把两者设成竞争关系，也不把AI设成替居民作出价值判断的“超级大脑”。**人类的智慧和硅基的智慧，都希望让我们的生活更加美好。** 人类提供价值、经验、伦理、情感、责任和最终判断；硅基智慧提供规模化感知、复杂推演、实时协同与持续学习。二者共同服务的对象，不是技术本身，而是人的生活、城市的公共利益与长期韧性。

共同目标不等于无限授权。**Civic AI Overlay 是规划层，C0-C6只是运行层。** 规划先回答“AI在什么空间、以什么对象、调用什么城市资源、拥有多大权限、谁负责、失败后如何降级”，七道联调门再回答“这套能力怎样从模拟进入有限真实运行”。每一个AI建议都先被视为假设，再经过规则与公共利益校核、影子运行、有限真实负载和人工监督；证据不足就停、风险不可控就退、公众利益不成立就不做。**智慧可以增加，权力边界必须清楚；系统可以越来越聪明，城市必须始终保留人的选择权。** 我们不是让AI替城市决定未来，而是让城市多一种理解自己、改善自己、与居民共同成长的能力。 [standard:PROJECT-AGENT-OPEN-CALL-TASKBOOK] [depth:risk_missing_data]

## 设计依据与资料清单

本方案的正式任务依据来自主办方公告、仓库 `design_brief`、面向智能体任务书、公共资料登记表和临时边界。方案方法同时吸收既有城市规划、市政基础设施、韧性城市、AIDC投产联调、AI赋能控规、城市更新与地下空间研究经验，但不把任何内部客户底图、非公开指标或项目成果上传至公共仓库；只迁移可普适的方法论。 [source:OFFICIAL-ANNOUNCEMENT] [source:AGENT-TASKBOOK] [source:SOURCE-REGISTRY]

核心专业判断有三条：第一，**AI进入城市以后，详规需要新增规划对象**——边缘算力接口、能源柔性接口、机器人物流接口、感知边界、运行权限、人工接管和退出条件不能继续停留在“运营层备注”；第二，**中心城区的AI基础设施必须做空间适配，而不是默认新增大型数据中心**，重点判断不同任务需要何种算力、何时用电、何种冷却与用水约束，因此本方案只强化 Compute / Power / Water 三项；第三，**公共利益必须被空间化**，AI入口之外必须同时存在人工入口、离线入口和低/无感知路径。由此形成“城市设计主体 + Civic AI Overlay + C/P/W专业支撑 + C0-C6运行方法”的清晰层级。 [standard:PROJECT-AGENT-OPEN-CALL-TASKBOOK] [depth:existing_conditions_diagnosis]

## 统筹研究范围产业与未来城市研究

### 1. 总体结构：城市设计主体 + Civic AI Overlay + AI基础设施适配 + 联调方法

**第一层｜城市设计主体。** 京张遗址公园形成连续公共脊，三处重点区承担不同的城市真实性：众智园验证AI研发与产品如何进入真实城市，AI原点社区验证AI如何服务人才与普通日常，大钟寺验证AI时代存量城市如何更新、如何形成可实施规则。公共空间、慢行、开放首层、社区生活和渐进更新先成立，AI再叠加其上。 [standard:MOHURD-URBAN-DESIGN-MEASURES]

**第二层｜Civic AI Overlay：本方案第一规划创新。** 它不是新增一种“AI用地”，也不替代法定控规，而是为传统详规补充一组AI时代的新规划对象，使“空间—接口—权限—责任—证据—退出”同时可被规划师、运营者和机器读取。

**最小规则单元：**  
`Rule ID → Spatial Scope → Object → Requirement/KPI → Source → Responsible Party → Permission → Commissioning Gate → Evidence → Version → Re-test Trigger → Rollback/Exit`

新增规划对象重点包括：边缘算力接口、能源柔性接口、感知范围、机器人物流/路缘接口、公共AI服务入口、自动系统权限、人工接管、低/无感知路径、维护隔离和复验/退出触发条件。传统用地、容积率、高度、道路和法定程序仍由正式规划与审批体系决定。

这次GitHub投稿要求GeoJSON、metrics、compliance、sources和版本记录，本方案把它视为一个原型证明：**未来的详细规划应当同时让人和机器读取。** 人读取空间意图、公共利益与实施逻辑；机器读取对象、边界、规则、状态和触发条件；两者必须指向同一份规划事实。

**第三层｜AI Infrastructure Support：Compute–Power–Water。** 基础设施不再建立“六网”总体叙事，只集中回答三个与AI产业最直接的空间适配问题：

|专项|核心规划问题|本方案规则|
|---|---|---|
|**C｜Compute Matching 算力匹配**|什么任务需要什么等级算力，什么算力适合留在京张？|区域算力承担大规模训练/高强度计算；片区算力服务承担推理、数字孪生、研发共享；边缘节点承担低时延、隐私敏感和高可靠任务。核心城区不默认新建大型AIDC。|
|**P｜Compute–Power Coordination 算电协调**|不是“有多少电”，而是何时、何地、什么任务必须运行、什么任务可调或迁移？|Protected保障负荷 / Flexible可调负荷 / Migratable可迁移负荷；结合储能、建筑柔性负荷和区域算力任务迁移。|
|**W｜Compute–Water Coordination 算水协调**|高密算力的冷却方式、水源和峰值用水是否适合中心城区？|W0边缘节点基本不新增显著冷却水需求；W1中小算力优先低水耗/闭式路线；W2高密算力同步论证能源、水与余热；W3高耗能高耗水任务原则上区域协同供给。|

通信、地下市政、交通和物流仍然必须设计，但作为**连接、工程和场景适配条件**进入专业图层，不与 C/P/W 抢同一原创层级。所有C/P/W结论只表达接口、状态、适配条件和触发机制，不虚构MW、MVA、m³/d、管径或工程线位。

**第四层｜C0–C6 + City Evidence Ledger：运行方法，不是第一原创点。** 七道门用于把已经被规划表达的AI能力从证据基线、模拟、规则校核、影子/假负载推进到有限真实负载、人工监督和复验/回滚/退出。Evidence Ledger记录Project ID、空间范围、责任主体、数据/模型版本、风险、权限、测试证据、人工介入和退出状态。它们负责“如何运行”，不再承担方案总体形态或主要原创性。

### 3. 品牌与视觉识别

主名称：**京张·城市联调带**；英文：**JING-ZHANG CITY COMMISSIONING BELT**。专业副标题：**AI时代的城市详规与真实场景创新｜A CIVIC AI OVERLAY FOR THE AI-NATIVE CITY**。核心识别不再依赖铁路隐喻或“七道门”，而使用“叠加层/接口/状态”的图形语法：传统城市底图上叠加一层可读规则网格，节点显示接口类型、权限和状态。**PROVE BEFORE SCALE** 与 **HUMAN OVERRIDE BY DESIGN** 保留为运行原则，而不是主品牌。 [standard:PROJECT-AGENT-OPEN-CALL-TASKBOOK]

## 总体设计范围城市更新与控规深度城市设计

总体设计不把AI设施叠加到一张普通城市设计上，而把物理基础设施、公共空间和治理规则作为同一设计对象。用地模型使用统一国土空间用地代码，形成科研—公园绿地—商业服务—社区服务的概念功能梯度；它只证明结构化表达和空间接口，不代表审定用地。 [data:geometry/land_use.geojson#LU-001] [standard:MNR-LAND-USE-CLASSIFICATION-GUIDE]

**Civic AI Overlay是本方案第一原创点。** 它对应AI时代详规需要新增的“空间接口与运行权利”对象，而不是再做一套城市OS。规则分三类：
- A Mandatory：安全、隐私、公共利益、人工接管、审计、应急不得绕过；
- B Conditional：允许以等效性能满足的条件性要求；
- C Guidance/Experimental：试点、创新和未来迭代。
每条规则采用 `Rule ID + Spatial Scope + Object + Requirement/KPI + Source + Responsible Party + Approval Gate + Version + Evidence + Re-test Trigger + Rollback/Exit`。

**更新策略：** 采用“体检—协商—策划—行动—联调—复验”的渐进更新逻辑。现阶段只给出保留适应、改造开放、新建测试设施、临时可逆使用四类概念动作；缺乏权属、结构、历史价值和法定控制条件时，不指定具体拆除建筑。 [standard:MOHURD-CONTROL-DETAILED-PLANNING] [depth:retain_renovate_demolish]

## 重点区域详细设计

![三处重点区域：测试、生活与更新的协同体系](assets/figures/key-areas.png)

### A. 众智园｜CITY TESTBED
众智园不是封闭实验园，也不是展示馆集合，而是“**AI产品进入真实城市之前的最后一公里**”。空间采用“公众前厅—受控测试核心—原型过渡带—有限真实接口”的风险梯度，并把 **PUBLIC / TEST / SERVICE** 三套流线物理分开。主要空间包括开发者共享前厅、模拟城市街道、自主系统测试院、市政AI影子运行室、维修与故障实验单元以及可插拔测试单元。 [data:geometry/key_areas.geojson#PROV-KEY-001]

C/P/W只在这里作为测试支撑：片区共享算力和边缘节点服务研发/推理；储能、负载模拟和应急切换用于算电联调；高密设备仅验证冷却与用水边界，不默认建设大型数据中心。测试通过只形成证据，不自动获得城市运行许可。

### B. 北京AI原点社区｜LIVING LOAD
这里不是“装满智能设备的未来社区”，而是检验AI能否在普通生活中长期工作的**真实生活负载**。空间以日常生活环、开放创新首层、社区共享客厅、全龄无障碍慢行和低感知安静空间为主体。 [data:geometry/key_areas.geojson#PROV-KEY-002] [standard:BARRIER-FREE-ENVIRONMENT-LAW]

公共服务执行四条等价路径：
- **AI PATH**：主动选择智能服务；
- **HUMAN PATH**：现场、电话或人工转接；
- **OFFLINE PATH**：无账号、断网、模型失效时仍能完成基础任务；
- **LOW / NO-SENSING PATH**：不愿进入持续感知环境的人仍能通行、停留并获得基本服务。

社区只部署满足低时延、隐私和可靠性需要的轻量边缘算力；不把居住区变成高强度训练设施。AI不是生活的前提条件，而是居民可以选择调用的一种能力。

### C. 大钟寺｜RENEWAL RULE LAB
大钟寺不是“AI商业综合体”，而是本方案最具规划专业含量的 **AI更新单元详规工作台**。它证明的不是“AI能生成几个更新方案”，而是AI时代的存量城市如何把多主体诉求、公共利益、片区—地块约束和实施状态转成可追踪的规划规则。 [data:geometry/key_areas.geojson#PROV-KEY-003] [depth:three_key_area_detailed_design]

空间动作采用 **KEEP / ADAPT / TEMPORARY / TRIGGERED** 四类，不在缺少权属、结构、文保和法定控制资料时预判拆建。工作流为：**现状证据 → 多主体协商 → 空间变量 → 公共利益校核 → 经济/实施可行性 → A/B/C规则 → 项目行动 → 一张图维护 → 使用反馈与复验。**

“更新议事厅”承载居民、商户、产权人、政府、运营者和专业团队协商；“片区—地块协同优化器”只生成可比较的空间组合；“规则账本”记录规则来源、责任、版本和触发条件。优先项目包括首层开放、步行商业连续性、社区设施补短板、适应性再利用、临时创新空间和共享后勤。存量建筑的轻型边缘算力只有在消防、电力、散热和维护条件满足时才接入；新增负荷或冷却需求分别触发Power / Water review。

AI可以辅助分析和方案比较，但不能自动决定容积率、产权、补偿、拆迁，也不能替代法定公众参与和审批。

## 交通、轨道、市政与公共服务设施

![交通慢行、公共空间与AI基础设施适配](assets/figures/mobility-bluegreen.png)

**交通与轨道。** 京张公共脊优先形成连续步行/自行车系统，并在三处重点区附近设置东西向缝合节点。路缘空间采用时分共享：上下客、配送、自主物流、应急和活动按时间与权限切换。自动驾驶/机器人测试必须有明确地理围栏、测试时段和人工接管规则。

**蓝绿与市政。** 海绵、生态、排水和内涝预测统一考虑，但AI预测不能替代实体排水能力和应急设施。通信、地下市政、维护、垃圾、物流等按常规专业逻辑提供可靠连接、检修和故障隔离，它们是场景成立的必要条件，不作为本方案独立原创主线。 [depth:municipal_public_services]

### AI Infrastructure Support｜AI基础设施适配系统

**C｜Compute Matching｜算力空间匹配。** 构建“区域算力—片区算力服务—边缘微节点”三级体系。大模型训练和高强度计算优先调用区域资源；片区级服务承担推理、数字孪生、科研开发和企业共享；众智园、AI原点及公共服务附近的小型边缘节点承担低时延、隐私敏感和高可靠任务。规划重点是算力任务与空间的匹配，不把“建设大型数据中心”作为默认答案。

**P｜Compute–Power Coordination｜算电协调。** 将计算任务分为 **Protected / Flexible / Migratable** 三类。公共安全、应急和关键公共服务属于保障负荷；普通推理、充电和部分企业计算可在时段内调节；可迁移训练/批处理任务可转移到区域算力资源。规划对象因此从单纯负荷预测扩展到“任务—时间—电力状态—储能—建筑柔性负荷”的协同，但不虚构现状可用容量。

**W｜Compute–Water Coordination｜算水协调。** 建立W0–W3适配规则：W0边缘节点原则上不形成显著新增冷却水需求；W1中小算力优先低水耗、闭式或与用途相称的冷却方式；W2高密算力必须同步论证能源、水资源、热排放与余热利用；W3对核心城区形成显著水电容量压力的任务原则上通过区域协同供给。图纸只标注冷却方式、水源条件、Peak Water Review触发，不虚构m³/d。

**三重点区角色：** 众智园重点是高可靠算力接口、测试算力、算电联调和机器人充换能；AI原点重点是轻量边缘推理、公共服务、低时延、低侵扰和应急供能；大钟寺重点是存量建筑适配、共享低成本算力接入和新增容量触发审查；京张公共脊只布置小型微节点，不建设“设备走廊”。

### 公共利益作为空间标准：四条等价路径

公共利益不只写成“关注老人、儿童、残障人士和隐私”，而要进入空间与服务验收。凡是承载基础公共服务的AI节点，原则上同时设计：

1. **AI入口**：允许主动使用智能服务；
2. **人工入口**：现场窗口、值守或人工转接可被直接看见；
3. **离线入口**：无账号、断网或模型不可用时仍能完成基础任务；
4. **低/无感知路径**：不愿进入持续感知环境的人仍能通行和使用公共空间。

这四条路径追求的是**基础公共服务结果等价**，而不是界面完全相同。典型验收包括：轮椅用户能否完成同一服务、老人能否不用商业账号办理、断网后是否仍有基础功能、系统是否明确显示人工责任与投诉/申诉入口。这样，AI伦理从宣言变成可画在平面、断面和节点图里的城市设计标准。 [standard:BARRIER-FREE-ENVIRONMENT-LAW] [depth:blue_green_public_space]
## 蓝绿空间、公共空间与城市风貌

京张遗址公园是“开放创新与公共审计脊”，而不是科技展廊。城市风貌强调真实街道、树荫、低门槛公共空间、铁路遗产连续叙事和小尺度数字界面。建筑体量采用“沿公共脊开放、重点节点形成识别、重点区内部适应产业需求”的原则，不在缺乏控规和文保资料时给出高度数值。 [standard:MOHURD-URBAN-DESIGN-MEASURES] [depth:blue_green_public_space]

公共节点采用“**三大核心荣誉节点 + 一个支撑型共享场**”的层级：
1. **First Run Yard｜首发试运行场**：铁路试运行历史与AI时代开放创新起点叠加；
2. **Open Evidence Hall｜开放证据厅**：展示开源方案、规则、数据来源、版本、贡献者、成功与失败证据；
3. **Civic Override Beacon｜公共接管灯塔**：让系统状态、有限权限、人工责任和退出机制在公共空间可见；
- **Commissioning Commons｜联调共享场**：作为开发者、居民、运维者共同交流、活动和临时测试的支撑型共享场，不列入“三大核心荣誉节点”。

结构化公共节点总数仍为4，用于满足机器可读数据与空间图层一致性；品牌传播只突出前三个核心节点。 [metric:ai_landmark_count]
